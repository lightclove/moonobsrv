# BUG-024 — setUpdateCursor: SQL не влезает в [96]u8 — резервный курсор в Postgres не пишется никогда

- Статус: ЗАКРЫТ (был ОТКРЫТ, закрыт 2026-09-09)
- Фикс: `src/bot/store.zig` (буфер 96 → 160) + тест на длину с maxInt(i64)
- Открыт: 2026-09-09
- Где найдено: код-ревью (злой QA, TC-103)
- Серьёзность: средняя

## Симптом

Курсор `tg_offset` в `bot_kv` никогда не обновляется (тихо). Документи-
рованная защита «курсор в файле + Postgres» наполовину мертва: если
state.json и /tmp-файл потеряны (свежий контейнер без волюма data), бот
откатывается к древнему курсору БД и перерабатывает старые апдейты.

## Причина

`src/bot/store.zig:249-252`: буфер `[96]u8`, а SQL
`INSERT INTO bot_kv (k, v) VALUES ('tg_offset', '{d}') ON CONFLICT (k) DO UPDATE SET v = EXCLUDED.v`
— 95 фиксированных байт + цифры update_id (реальные id — 9–10 цифр,
итого ~105). `w.print` падает `NoSpaceLeft` → `catch return`, exec не
выполняется. Ошибка тихая, тестов на длину не было.

## Лечение

Буфер ≥ 128 байт (95 + 19 цифр i64 + запас).

## Профилактика

Тест: `std.fmt.count` шаблона с максимальным i64 укладывается в размер
буфера (константу размера связать с тестом).
