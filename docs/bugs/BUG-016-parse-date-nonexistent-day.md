# BUG-016 — аргумент-дата: несуществующие дни месяца молча принимаются

- Статус: ЗАКРЫТ (был ОТКРЫТ, закрыт 2026-09-09)
- Фикс: `src/util.zig` (`daysInMonth`/`isLeapYear`, проверка в `parseDateArg`) + тест
- Открыт: 2026-09-09
- Где найдено: тесты (злой QA, прогон TC-067 из docs/TESTCASES_AAA.md)
- Серьёзность: средняя

## Симптом

Команды с датой принимают дни, которых не существует в указанном месяце, и
молча показывают небо другого дня:

- `/voc 31.02` → сводка на 3 марта;
- `/voc 30.02` → 2 марта; `/voc 31.04` → 1 мая; `/voc 31.06` → 1 июля;
  `/voc 31.09` → 1 октября; `/voc 31.11` → 1 декабря;
- `/voc 29.02.2026` (2026 — не високосный) → 1 марта.

Пользователь просит «31 февраля», получает чужой день без единого
предупреждения.

## Причина

`src/util.zig`, `parseDateArg`: проверяются только диапазоны
`1 ≤ month ≤ 12`, `1 ≤ day ≤ 31` — но не существование дня в конкретном
месяце/году. Алгоритм Хиннанта `daysFromCivil` корректно «переливает»
32-й день в следующий месяц, поэтому ошибки не возникает вовсе.

## Лечение

После разбора компонент сверять `day` с числом дней месяца (февраль — с
учётом високосности: год делится на 4, кроме столетий, не кратных 400);
несуществующий день → `error.BadDate` (пользователь получит стандартную
подсказку «Не понял дату…»).

## Профилактика

Тест в `src/util.zig` рядом с существующим `test "parseDateArg"`:
«31.02», «30.02», «31.04», «31.06», «31.09», «31.11», «29.02.2026» →
`error.BadDate`; «29.02.2028» — принимается.
