# BUG-018 — заявки на доступ не создаются: requestAccess недостижим

- Статус: ЗАКРЫТ (был ОТКРЫТ, закрыт 2026-09-09)
- Фикс: `src/bot/store.zig` (`Status.none`) + `src/bot/access.zig` (ветка `.none` → requestAccess + карточка)
- Открыт: 2026-09-09
- Где найдено: код-ревью (злой QA, TC-144)
- Серьёзность: критическая

## Симптом

На проде с `TELEGRAM_ACCESS_ID` и БД новый пользователь пишет `/start` —
получает «Заявка уже на рассмотрении. Ждите решения.» при том, что заявки
никогда не было. Админу карточка не приходит; «Пустить» человека нечем —
команды /allow нет, единственный путь входа (кнопка на карточке) не
наступает никогда. Противоречит README («админу приходит карточка с
кнопками Пустить / Отклонить») и слайду гида «Доступ».

## Причина

`src/bot/access.zig:54-64`: switch по `statusOf` покрывает все три варианта
enum (`active`/`denied`/`pending`) и каждая ветка завершается `return` —
код после switch (вызов `store.requestAccess` — единственное место,
создающее заявку и карточку) недостижим. А `store.statusOf`
(`src/bot/store.zig:368`) для неизвестного пользователя (нет строки в
`app_user`) возвращает `.pending` — ветка «неизвестный» неотличима от
«уже подал».

## Лечение

Различить «нет строки» от «pending»: расширить `Status` вариантом `none`
(или `?Status`), `statusOf` возвращает `none` при отсутствии строки;
`handleUnknown` для `none` выполняет существующий путь `requestAccess` +
карточка админу. (Вместе с этим закрыть BUG-025 — на ошибке PG тоже
возвращать не-.active.)

## Профилактика

Юнит-тест на `handleUnknown`-путь не построить без фейк-API, поэтому:
(1) тест на `statusOf`-семантику «нет строки → none», (2) ручная проверка
E1–E3 из MANUAL_TESTING.md в чек-листе релиза.
