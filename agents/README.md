# agents/README.md — обвязка агентов moonobsrv

Универсальная обвязка для работы агентов над проектом: роли, протоколы,
артефакты, воркфлоу, память. Подключена к шести MCP-серверам (`.mcp.json`):

| MCP | Зачем |
| --- | --- |
| `lsp` (agent-lsp + zls 0.15.1 из `tools/zls/`) | семантика Zig: go-to-definition, find_references, blast_radius, diagnostics, безопасный rename, speculative edit. Роутер `.zig` → zls, тёплая сессия живёт между ходами агента |
| `fetch` (mcp-server-fetch, uvx) | внешние ссылки: документация Zig 0.15, Bot API Telegram, RFC (1928, 3986), астрономические эталоны для якорей |
| `git` (mcp-server-git, uvx, `-r <корень>`) | история и дифы без shell: статус, лог, blame по файлу; сверка «коммит ↔ changelog ↔ карточки» (архивариус, аудитор) |
| `time` (mcp-server-time, uvx, Europe/Moscow) | точное время и часовые пояса: даты changelog-записей, якоря в разных поясах, границы суток (QA, аудитор) |
| `memory` (@modelcontextprotocol/server-memory, npx) | граф знаний `agents/memory/memory.json`, живёт между сессиями: факты о проекте, грабли, решения — по схеме `agents/memory/README.md` |
| `sequential-thinking` (npx) | сложные многошаговые рассуждения: разбор бага с гипотезами, планирование рефакторинга, ретроспектива прогона |

GitHub-задачи (issues/PR репозитория lightclove/moonobsrv) — через `gh` CLI
(уже авторизован); отдельный github-MCP не подключён: официальный сервер
deprecated и требует личный токен в конфиге.

Языки агентов: размышления и ответы — русский; код, идентификаторы, пути — как в проекте.

## Роли

| Агент | Файл | Мандат |
| --- | --- | --- |
| Разработчик | [developer.md](developer.md) | превратить задачу в код + тесты + документацию |
| Ревьюер | [reviewer.md](reviewer.md) | найти проблемы до продакшена; ничего не менять |
| Злой QA | [qa-evil.md](qa-evil.md) | сломать то, что написали; ничего не чинить |
| Аудитор | [auditor.md](auditor.md) | вахты над работающей системой: учёт, соак, прод (read-only) |
| Архивариус | [archivist.md](archivist.md) | гигиена истории и релизов: changelog, версии, теги, коммиты |

Роли ортогональны: разработчик не одобряет свой код, ревьюер не пишет фичи,
QA не правит баги, аудитор не трогает код и прод, архивариус не релизит —
готовит выкат, жмёт кнопки владелец. Один агент может играть роли по
очереди, но не в одном ходу.

## Общие правила (для всех ролей)

1. **Сначала контекст, потом действие.** Перед любым изменением — прочитать
   `AGENTS.md`, задеть затрагиваемые модули (чтение или MCP `lsp`), свериться
   с существующим стилем. Никаких предположений о содержимом файлов.
2. **Зависимости.** В проекте ноль внешних зависимостей — так и должно
   остаться. Новая «нужная библиотека» — сначала вопрос владельцу, не код.
3. **Архитектура.** Зависимости строго вниз (см. `docs/OVERVIEW.md`, раздел 5):
   небо не знает про сеть, фичи не знают про сокеты. Астроядро — чистые
   `f64 → f64` без аллокатора.
4. **Буферы.** Локальные буферы фиксированные (`std.Io.Writer.fixed`), размеры
   подобраны; SQL и JSON собираются в буфер с запасом. Арену — на запрос/тик,
   `page_allocator` — только для долгоживущего. Утечка в цикле = баг-карточка.
5. **Комментарии** — редко и только «зачем». Не описывать изменения
   комментариями, не общаться с пользователем через код.
6. **Тесты.** `z.cmd build test` — обязательный шлюз. Новая возможность —
   новый тест (юнит-тест в модуле или якорь в `src/tests.zig`).
7. **Учёт** (по `AGENTS.md`): правка поведения → `docs/CHANGELOG.md` `[Unreleased]`
   тем же ходом; баг → карточка `docs/bugs/BUG-NNN-slug.md` + строка на доску
   `docs/BUGS.md`; план → `docs/BACKLOG.md`.
8. **Деплой.** `deploy.cmd` трогает прод (Arch 192.168.31.11) — только по
   явному указанию владельца. `deploy.cmd -Status` — безопасен.
9. **Секреты.** Токены живут только в `.env` (в git не попадают). Никогда не
   вставлять токен в код, тест, лог, коммит.

## Воркфлоу (конвейер)

```
задача ──► DEVELOPER ──► код + тесты + changelog
                │
                ▼
           REVIEWER ──► замечания (блокирует / не блокирует)
                │  ▲
                ▼  │ правки
           DEVELOPER
                │
                ▼
             QA-evil ──► баг-репорты (карточки BUG-NNN)
                │  ▲
                ▼  │ лечение
           DEVELOPER ──► все тесты зелёные, changelog пополнен
                │
                ▼
           AUDITOR ──► вахта: учёт, соак, прод read-only
                │
                ▼
          ARCHIVIST ──► релиз-комплект (записи, версии, теги, коммиты)
                │
                ▼
            владелец: релиз + deploy.cmd (по решению человека)
```

Правила передачи:

- **Definition of Done** у разработчика: `z.cmd build test` зелёный,
  changelog-запись есть, замечания ревьюера закрыты, карточки QA — в статусе
  ЗАКРЫТ или осознанно отложены владельцем.
- Ревьюер и QA **не чинят** — только документируют. Так находят разное:
  ревьюер смотрит код, QA — поведение.
- Аудитор подключается на готовой сборке (после QA или между релизами —
  плановые вахты); находит расхождения учёта и поведения длинных циклов.
- Архивариус собирает релиз-комплект, когда `[Unreleased]` не пуст, тесты
  зелёные и вердикт ревьюера APPROVE; релизная сборка проверена (урок
  BUG-065).
- Баг-репорт QA — сразу карточкой по шаблону `docs/bugs/_TEMPLATE.md`,
  номер — следующий свободный NNN на доске.
- Спор между ролями (например, «это не баг, а фича») решает владелец.

## Карта проекта (для быстрой ориентации)

```
src/astro*.zig        чистое астроядро (Meeus, Standish; бисекция по «пиле»)
src/net/              SOCKS5 (RFC 1928) + свой HTTPS/TLS 1.3 over Tor
src/db/pg.zig         клиент PostgreSQL wire-протокола v3
src/bot/              telegram, router, store (PG/JSON), wd (сторожа+Docker),
                      mon (/monitor, idle), rst (рестарты, стоп-краны),
                      access (whitelist/заявки), cb (колбэки), keys
src/features/         фичи: команды + on_tick; реестр на comptime
src/main.zig          цикл polling, watchdog, CLI (--today, watch)
build.zig             ReleaseSmall, strip, gc-sections
z.cmd                 обёртка тулчейна (zig из PATH или tools/)
```

Сборка и проверки: `z.cmd build test` (тесты), `z.cmd build -Drelease`
(релиз), `z.cmd build -Drelease -Dtarget=x86_64-linux-musl` (прод-бинарь).

## MCP lsp — как пользоваться

- Быстрая разведка символа: `explore_symbol` / `inspect_symbol` (hover).
- Перед правкой публичного: `blast_radius` — все вызовы и экспорты разом.
- Перед rename: `prepare_rename` + превью всех мест, потом применять.
- Спекулятивная правка: `simulate_edit` / `safe_apply_edit` — диагностическое
  дельта без записи на диск.
- После правки: `get_diagnostics` по тронутым файлам + `z.cmd build test`.
- Первая сессия индексирует workspace (~10 с), дальше — тёплая.

## MCP fetch — как пользоваться

- Ссылки в задачах (RFC, Bot API, астрономические таблицы) — читать через
  `fetch`, не выдумывать содержимое.
- Для якорей брать даты из внешних источников (timeanddate, astrostar,
  альманахи) и сразу вносить в тест с допуском из README «Точность и
  соглашения».

## MCP git — как пользоваться

- История без shell: `git_status`, `git_log`, `git_diff` (uncommitted /
  staged), `git_show` — сверять «коммит ↔ changelog ↔ карточка».
- `git_diff_unstaged` перед коммитом — не зацепить чужие правки (в рабочем
  дереве могут лежать незакоммиченные правки владельца).
- Коммитит всё равно shell (`git add` + `git commit`) — по правилам
  архивариуса, пуш только владелец.

## MCP time — как пользоваться

- Дата записи changelog и карточки — текущая по Europe/Moscow, не по UTC
  (проект живёт в МСК).
- Якоря из внешних источников в чужих поясах — переводить явно
  (`convert_time`), допуск не съедать.

## MCP memory — как пользоваться

- Начало сессии: `search_nodes` по теме задачи — что уже известно, какие
  грабли пойманы.
- Конец сессии: записать факты (схема — `agents/memory/README.md`):
  новые инварианты, найденные баги (`BUG-NNN`), решения (`D-NN-*`),
  чем кончилась сессия (`S-<дата>-<роль>`).
- Дубли не создавать; устаревшее помечать `obsolete`, не удалять.
- Секреты — никогда.

## MCP sequential-thinking — как пользоваться

- Включать на сложном: разбор бага с несколькими гипотезами, планирование
  рефакторинга через этажи, ретроспектива прогона QA.
- Каждый шаг — одна мысль с номером; гипотезы ревизовать явно
  (`nextThoughtNeeded`), не тащить опровергнутое в вывод.

## Память обвязки

- Граф знаний живёт в `agents/memory/memory.json` (MCP `memory`), схема и
  правила записи — [memory/README.md](memory/README.md).
- Стартовый граф: проект, этажи astro/net/db/bot/features, обвязка агентов.

## Проверка обвязки

```
agent-lsp doctor zig:C:/Users/admin/Work/moonobsrv/tools/zls/zls.exe
                                    :: зиг-семантика жива (абсолютный путь!)
uvx mcp-server-git -r C:/Users/admin/Work/moonobsrv --help
                                    :: git-сервер на месте
uvx mcp-server-time --local-timezone Europe/Moscow --help
                                    :: time-сервер на месте
z.cmd build test                    :: 104+ теста зелёные
```

Примечание: `--help` у stdio-MCP-серверов может висеть (сервер ждёт stdin) —
это не сбой; признак живости — вывод справки до таймаута.
